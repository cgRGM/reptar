# Plan: Calibrated Benchmark App (Reptar vs .NET Minimal API vs Hono)

Status: **implemented (first pass)** — see `bench/` and `bench/README.md`. Scope: `bench/` apps, shared schema/seed, load harness, VPS methodology.

Related: `README.md` (benchmarks), `design.md` §12 (performance targets), `examples/realworld`, `examples/campfire`, `bench/results`.

---

## 0. TL;DR

Don't add a third third-party app. Build **one small, realistic multi-tenant issue-tracker API** ("Reptar Bench") and implement the exact same schema, SQL, JSON, and routes in:

1. **Reptar Native AOT** (Kestrel)
2. **.NET 10 Minimal API Native AOT** (Kestrel) — the control
3. **Hono on Bun** (JIT and compiled bundle)

Run a **complexity ladder** of endpoints so the report separates HTTP/routing/JSON/validation/DB/auth overhead instead of collapsing everything into one DB-bound number. Keep RealWorld and Campfire as the spec-compliance and realtime benchmarks; use this app for framework-overhead and realistic-capacity questions.

## 0.1 As built (implementation notes)

The first implementation is in `bench/` and differs from the proposal in four places, all discovered while making the AOT build work:

1. **Auth uses stateless HS256 JWTs, not a `tokens` table.** This isolates the PBKDF2 + JWT cost and avoids a SQLite write on every login. The fixture JWT is generated by `bench/shared/seed.ts`.
2. **The update tier is `PUT`, not `PATCH`.** Reptar has no `Patch` route helper today; adding one is a separate framework change.
3. **Reptar uses a source-generated `JsonSerializerContext`** via `ReptarConfig.Json = new BenchJsonCodec()`. The default `ctx.Json<T>` codec uses reflection and trims nested DTO properties under Native AOT (responses serialize as `{}`). The source-gen codec is the production-safe path and is also what the Minimal API control uses.
4. **Reptar uses manual validation, not `Rule<T>`.** `Rule<T>` compiles expression trees and throws under Native AOT. The benchmark app validates manually, matching the Minimal API control. This is a finding: `Rule<T>` needs a source-generated path before it can be the default AOT story.

### Post-optimization results (HEAD `223ac88`)

The framework landed zero-allocation routing, direct UTF-8 JSON, a PipeWriter/lazy-header Kestrel host, an enhanced `[ReptarEntity]` generator with a positional fast path, a 32-connection `Mode=ReadOnly` SQLite read pool, zero-allocation JWT/PBKDF2, pre-gate write command building, SQLite group-commit batching, one-query auth, and SQLite-only AOT trimming. Clean 3-stack run on the same VPS (zero non-2xx, empty server log):

- T0/T1/T2/T3 (plaintext/JSON/router/validation) are **41.9k/42.2k/41.4k/36.3k req/s** — at or above raw .NET Minimal API.
- DB-heavy tiers: T4 detail **13.8k**, T5 list **5.9k**, T6 comments **10.7k**, T7 create **6.2k**, T8 `/me` **15.7k**, T10 update **4.9k**.
- **Reptar wins 10 of 12 tiers vs .NET Minimal API** (T0 tie, T9 PBKDF2-bound, mixed -2%). It is a near-clean sweep on the constrained VPS.
- Hono still wins plaintext, single-row reads, lists, login, updates, and the mixed blend; Reptar wins JSON, routing, validation, comments, creates, and `/me`.
- Group commit cut the T7 write gate **26.3 ms -> 2.8 ms** and moved T7 **3.5k -> 6.2k** (+77%). The insert is 0.114 ms p50; auth 0.027 ms p50.
- T8 one query: **12.1k -> 15.7k** (+29%). T10: **3.7k -> 4.9k** (+35%).
- Binary **10.4 MB**, startup **124 ms**. RSS under write load is 83–103 MB, higher than Minimal API/Hono; the read pool/group-commit buffers are the likely cause.
- SWR-cached reads: T4 **39.2k**, T5 **29.9k**, T6 **35.5k** req/s (3.4x–5.6x over uncached).

The remaining gaps are read-path efficiency vs Hono (T4/T5), plaintext (T0), PBKDF2 (T9), and mixed (T11) — not the router, serializer, or auth. See `bench/results/FINDINGS.md` for the full tables and recommendations.

## 1. Why another app

- **RealWorld is DB-bound.** The README's own numbers show it: `/api/tags` 4,220 req/s vs `/api/articles` 901 req/s. The gap is query complexity, not framework code. It is a great spec test, but a weak framework-overhead test.
- **Campfire is realtime-bound.** It measures Action Cable/WebSocket fan-out, not HTTP throughput.
- **Hello-world measures only the best case.** It tells you the ceiling, not where the ceiling comes from.
- **.NET Minimal API is the perfect control.** Same language, same runtime, same Kestrel, same Native AOT. The delta is the framework itself.
- **Hono is the design inspiration and the JS/edge baseline.** It shows whether a C# AOT framework can compete with the fastest JS router on Bun.
- The useful question is: **at each layer, how much does Reptar add over raw .NET, and how does it compare to Hono?**

## 2. The app: "Reptar Bench" issue tracker

A Linear/GitHub-Issues-shaped API: users belong to orgs, orgs have projects, projects have tasks, tasks have comments. It is familiar, realistic, and exercises every layer without inventing a fake domain.

### 2.1 Schema (SQLite, WAL)

```sql
users(id TEXT PRIMARY KEY, email TEXT UNIQUE NOT NULL, name TEXT NOT NULL, created_at TEXT NOT NULL)
tokens(id TEXT PRIMARY KEY, user_id TEXT NOT NULL, token_hash TEXT UNIQUE NOT NULL, created_at TEXT NOT NULL)
orgs(id TEXT PRIMARY KEY, name TEXT NOT NULL, slug TEXT UNIQUE NOT NULL, created_at TEXT NOT NULL)
projects(id TEXT PRIMARY KEY, org_id TEXT NOT NULL, name TEXT NOT NULL, key TEXT NOT NULL, created_at TEXT NOT NULL)
tasks(id TEXT PRIMARY KEY, project_id TEXT NOT NULL, author_id TEXT NOT NULL,
      assignee_id TEXT, title TEXT NOT NULL, description TEXT NOT NULL,
      status TEXT NOT NULL, priority INTEGER NOT NULL,
      created_at TEXT NOT NULL, updated_at TEXT NOT NULL)
comments(id TEXT PRIMARY KEY, task_id TEXT NOT NULL, author_id TEXT NOT NULL,
         body TEXT NOT NULL, created_at TEXT NOT NULL)
```

Indexes:

```sql
CREATE INDEX tasks_project_status_created ON tasks(project_id, status, created_at DESC);
CREATE INDEX tasks_assignee_status ON tasks(assignee_id, status);
CREATE INDEX comments_task_created ON comments(task_id, created_at);
CREATE INDEX projects_org ON projects(org_id);
CREATE UNIQUE INDEX tokens_hash ON tokens(token_hash);
```

### 2.2 Seed data

Deterministic, fixed RNG seed:

- 1,000 users
- 10 orgs
- 100 projects
- 50,000 tasks (500 per project)
- 250,000 comments (5 per task)
- 1,000 API tokens (one per user)

IDs and timestamps are fixed so every implementation returns identical bytes (except cursor encoding). A generated `bench/shared/fixtures.json` holds sample IDs, tokens, and project/task IDs for the load scripts.

### 2.3 Endpoints / complexity ladder

| Tier | Route | What it isolates |
| :-- | :-- | :-- |
| T0 | `GET /__bench/plaintext` | HTTP stack + routing (raw text) |
| T1 | `GET /__bench/json` | + JSON serialization |
| T2 | `GET /__bench/router/:orgId/:projectId/:taskId` | + route matching + params |
| T3 | `POST /__bench/validate` | + body parsing + validation |
| T4 | `GET /api/v1/tasks/:id` | + one DB read + row mapping |
| T5 | `GET /api/v1/projects/:projectId/tasks?status=open&limit=20` | + list query + pagination |
| T6 | `GET /api/v1/tasks/:id/comments?limit=20` | + nested list / join |
| T7 | `POST /api/v1/projects/:projectId/tasks` | + DB write |
| T8 | `GET /api/v1/me` (Bearer) | + auth middleware + user lookup |
| T9 | `POST /api/v1/auth/login` | + PBKDF2/Argon2 crypto |
| T10 | `PATCH /api/v1/tasks/:id` | + update + optimistic concurrency |
| T11 | Mixed workload (70/20/10 read/list/write) | realistic capacity |

The `__bench` routes are calibration only; the `api/v1` routes are the realistic app. Optionally register 100 dummy routes behind `BENCH_ROUTE_COUNT` to test router scaling without changing the app.

### 2.4 Response contract

- Same field names, types, and nullability in all three implementations.
- `GET /api/v1/tasks/:id` returns the task with an `assignee` object.
- List returns `{ "data": [...], "nextCursor": "..." }`.
- Create returns `201` with the created task.
- Validation errors return `422` with `{ "error": { "code": "validation_error", "issues": [...] } }`.
- Auth errors return `401` with `{ "error": { "code": "unauthorized" } }`.
- ISO-8601 UTC timestamps everywhere.

### 3.1 Reptar

- File-based C# app (`app.cs`) with `#:project ../../framework/Reptar/Reptar.csproj` and `#:project ../../framework/Reptar.Kestrel/Reptar.Kestrel.csproj`.
- `ReptarApp.Create(new ReptarConfig { Database = Db.Sqlite(...) })`.
- `Rule<T>` for the validation tier; `Jwt` for auth; raw SQL through `ctx.Db`.
- Telemetry off for the main run; a separate run with `RequestId()` + `Telemetry()` measures their overhead.

### 3.2 .NET Minimal API (control)

- `WebApplication.CreateSlimBuilder`, `ListenAnyIP`, no HTTPS.
- Raw `Microsoft.Data.Sqlite` (no EF Core, no Dapper) so ORM differences don't swamp framework differences.
- Source-generated `JsonSerializerContext` for AOT.
- `PublishAot=true`, `InvariantGlobalization=true`, `DebugType=None`.
- Manual validation and manual HMAC/JWT lookup to mirror Reptar's path as closely as possible.

### 3.3 Hono

- `Bun.serve({ fetch: app.fetch })`, `bun:sqlite` with prepared statements.
- Zod + `@hono/zod-validator` for the validation tier; `hono/jwt` for auth.
- Two builds: `bun run src/index.ts` (JIT) and `bun build --compile` (standalone bundle). Report both, and label the compiled bundle as a bundle, not AOT.

### 3.4 No ORM

Deliberate: raw SQL in all three. The benchmark is about the framework, not the ORM. If we want an ORM axis later, it becomes a separate dimension.

## 4. Fairness rules

- Same seeded SQLite file per implementation (copy it; don't share a writer).
- Same WAL settings: `journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout=5000`.
- Same queries, same indexes, same response bodies.
- Same middleware behavior: request ID optional, CORS off, telemetry off for the main run.
- Same keep-alive, HTTP/1.1, no TLS.
- Same Kestrel settings for both C# apps (`CreateSlimBuilder`, `ListenAnyIP`, no HTTPS, no IIS).
- Same .NET AOT settings.
- Document where idiomatic paths differ:
  - Reptar's `Ctx.Json<T>` serializes to a string, then UTF-8 bytes.
  - Minimal API writes JSON directly to the response stream.
  - Hono uses `JSON.stringify` and Bun's response path.
- Document that Bun's `bun:sqlite` is synchronous and single-connection. That is a real Hono-on-Bun constraint, not a benchmark bug.

## 5. Benchmark methodology

### 5.1 Hardware reality

The Lightsail instance is **2 vCPU = 2 SMT threads on 1 physical core**, 3.7 GB RAM, Ubuntu 24.04. Server and load generator on the same box compete for the same physical core.

Two modes:

1. **Relative mode (start here):** `taskset` the server to CPU 0 and `oha` to CPU 1. Same conditions for all frameworks. Good for ranking; not absolute capacity.
2. **Absolute mode (recommended for final numbers):** a second Lightsail instance in the same region as the load generator. Open only the benchmark port in the Lightsail firewall and restrict it to the loadgen IP. This gives clean absolute numbers.

### 5.2 Load tool

- `oha` (Rust, PGO build) for per-endpoint runs. It is efficient, supports `-c`, `-z`, `-q`, JSON output, and latency percentiles.
- `k6` or a small Bun driver for the mixed workload (T11).
- Warmup 3s, measure 10s, 3 repetitions, report the median.
- Run `-c 10`, `-c 100`, and `-c 500` to get a concurrency curve, not a single point.
- Use `--latency-correction` for fixed-rate runs to avoid coordinated omission.

### 5.3 Metrics

Per implementation and tier:

- RPS (requests/sec)
- p50 / p90 / p95 / p99 latency
- success rate / error distribution
- CPU % and CPU time per request (`pidstat`, `/proc/<pid>/stat`)
- RSS after warmup
- binary size and container image size
- cold start to first `200`
- build time (secondary)
- lines of app code (secondary; ergonomics, not perf)

### 5.4 Controls

- Disable Docker logging (`--log-driver none`) or run binaries directly.
- Run one server at a time; stop the other containers.
- Warm the SQLite page cache for read tiers; reset the DB copy for write tiers.
- Record the exact commit, binary hashes, kernel, CPU governor, and command lines in `manifest.json`.
- Check whether the instance is burstable and whether CPU credits are available; note it in the report.

## 8. Risks / open questions

- **SQLite single-writer** limits T7/T10. If writes dominate, add a Postgres variant of the write tier.
- **Bun's `bun:sqlite`** is synchronous; Hono's DB concurrency will be lower than the C# apps'. That is a real deployment constraint, not a bug. Report it explicitly.
- **Reptar JSON is reflection-based under AOT** (`DefaultJsonCodec` + `ReptarJson.Options`). Minimal API can use source-gen. This is a real difference and a likely Reptar optimization.
- **Reptar's router is a linear scan** with a `Dictionary` allocation per match (`ReptarApp.Match`). With ~15 routes it may be fine; with 100+ it will not. Use `BENCH_ROUTE_COUNT` to test.
- **Reptar's Kestrel host** copies the body into a `MemoryStream`, copies headers into a `Dictionary`, and writes the response body. A tiered benchmark will quantify that overhead vs raw Minimal API.
- **Public port 8787 is blocked** by the Lightsail firewall. For remote loadgen, open only the benchmark port and restrict the source IP.
- **The instance is burstable/shared.** Absolute numbers may vary. Report medians and CPU credits.
- **Hono compiled bundle is not AOT.** Label it correctly.
